# ADR-0006 — 配置单文件 + 原子写 + 损坏保护（含"为什么不拆分"论据）

状态：已采纳 ｜ 日期：2026-10-24

## 背景

全部配置（服务 + 路由 + 全局设置）持久化在单个 `polymock.config.json`，注册表每次变更全量落盘。曾经出现的两个风险：

1. 写入中断（进程被杀 / 磁盘满）留下半个 JSON 文件；
2. 用户手改配置出语法错误（多余逗号 / BOM / 截断）后，`loadState` 解析失败返回空状态，随后第一次注册表变更把空状态**原子覆盖**原文件——原本可救的数据被静默清空。

## 决策

1. **原子写**：保存先写临时文件（`<路径>.<pid>.tmp`）再 `rename`，任意时刻磁盘上的配置文件要么是完整的旧版、要么是完整的新版（`src/store.ts`）。
2. **损坏保护**：`loadState` 解析失败时，先把原文件整体保留为 `<原路径>.corrupt-<时间戳>` 副本（rename 自身失败时降级为仅日志、原文件保持原位），再按空配置启动——坏文件永远可人工恢复。
3. **单文件不拆分、不加写节流、不限制 body 大小、不做 body 外部文件引用**，论据：
   - 拆分（服务/路由分文件）会丢掉"一次 rename 即完成全量切换"的原子性，多文件写入没有廉价的事务手段；
   - 写节流（防抖后落盘）会扩大"崩溃丢最近 N 秒变更"的窗口，与"每次变更即落盘"的直观语义冲突；
   - 限制 body 大小改变产品语义（用户就是要 mock 大响应）；外部文件引用引入"配置 + 附件"两套一致性，收益配不上复杂度。
   - 当前体量（本地开发工具，配置通常 < 几 MB）下，全量 JSON.stringify + rename 的成本毫秒级，无性能压力。

## 后果

- 任一时刻配置文件都是合法完整快照；坏文件必有副本可救。
- 代价：大配置下每次变更全量重写（可接受）；`corrupt-*` 副本需要用户手动清理；`loadState` 对语法正确的语义错误（如缺字段）仍按缺省兜底，不做逐项校验。
